Arquitetura da aplicação de monitoramento legislativo do Senado Federal. O frontend consome uma API própria, que coordena os casos de uso, a persistência local e a integração com os Dados Abertos do Senado. Selecione os componentes do diagrama para consultar suas responsabilidades.

2 · Responsabilidades das camadas

Frontend

HTMLCSS JavaScript

Apresenta os dados e recebe interações do usuário. O ApiClient centraliza as chamadas para a API interna.

API

FastAPIREST

Expõe endpoints, valida parâmetros e encaminha as operações para os casos de uso. Não deve concentrar regras de negócio.

Application

Use Cases

Orquestra operações como sincronização de proposições, consulta e cálculo de estatísticas.

Domain

SOLIDPorts

Contém conceitos, regras e contratos centrais. Não depende de FastAPI, HTTPX ou SQLAlchemy.

Infrastructure

AdaptersSQLAlchemy

Implementa os contratos do domínio e conecta o sistema ao banco de dados e à API externa do Senado.

3 · Fluxo de sincronização

1. Disparo

A sincronização pode ser iniciada pelo endpoint POST /api/v1/sync, na inicialização ou pelo agendamento periódico.

2. Caso de uso

A camada Application coordena o processo e utiliza a abstração de integração com o Senado.

3. Integração

O adaptador SenadoApiClient consulta os serviços externos e entrega os dados à aplicação.

4. Persistência

O repositório concreto normaliza e persiste as proposições no banco local.

Importante: o intervalo configurado para sincronização automática é de seis horas. A integração externa ainda precisa de validação real em ambiente com acesso à API do Senado.

6 · Princípios arquiteturais

Dependency Inversion

Os casos de uso dependem de contratos, não de implementações concretas de banco de dados ou HTTP.

Repository Pattern

A persistência é acessada por uma abstração, implementada atualmente com SQLAlchemy.

Adapter Pattern

Os adaptadores traduzem as interfaces externas para os contratos internos da aplicação.

Clean Architecture

As regras de domínio permanecem independentes de frameworks, banco de dados e serviços externos.

7 · Estratégia de evolução do banco

Atual

SQLite

Banco inicial, configurado por DATABASE_URL.

Futuro

PostgreSQL

Substituição do adaptador de persistência e configuração da conexão, preservando contratos e regras de negócio.

SQLAlchemy e Alembic fornecem a camada de ORM e migrações. A migração deve ser testada para garantir compatibilidade de tipos, índices, constraints e consultas.

9 · Limitações e pontos de atenção

Integração externa: a sincronização com a API real do Senado não foi validada na implementação anterior, devido a uma falha de resolução DNS no ambiente de desenvolvimento.
  • Validar os payloads reais dos endpoints externos.
  • Verificar os vínculos entre processo, matéria e parlamentar.
  • Implementar a coleta estruturada de votações nominais.
  • Implementar a coleta de autoria, tramitação e relatorias.
  • Não apresentar estatísticas de dados que ainda não foram coletados.
  • Revisar a estratégia de sincronização e histórico incremental.
